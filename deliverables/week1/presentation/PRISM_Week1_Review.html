01 · Understanding

The problem PRISM solves

Campus placements are the most important outcome of an engineering degree — yet preparation for them is fragmented, unverified, and unmeasured.

Problem 01

Fragmented

Mentorship, mock interviews, résumé help, coding practice and study material live in separate, disconnected tools.

Problem 02

Unverified

No curated, mentor-vetted source of resources or questions — anyone can share anything.

Problem 03

Unmeasured

Neither the student nor the department can see whether preparation is actually improving readiness.

PRISM answers all three: one role-based, auditable platform where mentors produce trusted content, mentees practise, and progress is recorded.

01 · Understanding

Project objectives

  • Connect mentees with mentors — book, meet over video, get feedback, rate.
  • Teach 1:1 and 1:many — mentorship sessions plus mock interviews and group discussions.
  • Practise without a human present — AI interviewer, a 6-round Interview Game, AI-moderated GD.
  • Build strong résumés — structured builder plus AI résumé-vs-job-description analysis.
  • Trusted resources — mentor-uploaded material tagged by topic, company and level.
  • Make progress visible — per-student tracking and analytics dashboards.

O8 — Safe & reliable enough for real, college-wide use

Production hardening: authentication, access control and data integrity. This is the Week 1 engineering focus.

01 · Understanding · Users

Three roles, enforced on the server

Mentee

The student

Books sessions, takes AI mocks & the Interview Game, builds and analyses a résumé, solves coding problems, studies, and tracks where they stand.

Mentor

Senior / placed / faculty

Publishes availability, runs 1:1 and group sessions, uploads trusted resources, and leaves structured feedback that feeds a mentee's progress record.

Admin

Placement coordinator

Manages users, curates topics and companies, moderates content, and views platform-wide analytics and leaderboards.

The role is stored on the user and checked on every protected action — never trusted from the client.

02 · Proposed Workflow

The core mentorship loop

Mentor publishes availability │ Mentee browses → books a slot │ (atomic: no double-booking) ▼ Mentor approves / rejects → notified │ ▼ Both join a peer-to-peer video call │ ▼ Session completed → both rate (updates mentor average)
  • Booking is atomic — a single conditional database write guarantees two mentees can never grab the same slot.
  • Status machine — pending → approved → in-progress → completed, with rejection and cancellation paths.
  • Rate-once — a guard prevents double-rating; mentee ratings roll up into the mentor's average.

Alongside this loop, solo practice — AI interview, Interview Game and résumé tools — is available any time, with no mentor required.

03 · Requirements · Non-Functional

What turns a demo into a product

Security

Auth on every endpoint · authorization by role and ownership · server-authoritative scoring (no tampering) · sandboxed code · authenticated realtime · secrets never leaked.

Reliability

Fail-fast on misconfiguration at boot · categorized errors (4xx vs 5xx, not all 500) · every request traceable by request-id.

Performance

Hot queries use indexes — no collection scans · list endpoints are paginated and bounded.

Integrity & scale

No double-booking under concurrency (atomic writes) · abuse-resistant via tiered rate limits · stateless HTTP, designed for multiple processes.

Each non-functional requirement maps to specific, verifiable Week 1 engineering work.

04 · Database Design

MongoDB via Mongoose — design principles

  • Document-shaped data — résumés, games and availability are naturally nested; one document replaces 4–5 SQL joins.
  • Mongoose imposes a schema — types, required, enum, validation give flexibility and structural guarantees.
  • Embed data owned by its parent (game rounds, résumé sections, availability slots).
  • Reference shared entities (User, Topic, Company, Resource) that have their own lifecycle.
  • Index only the fields real queries filter or sort on → O(log n), not a full scan.
  • Let the database enforce what it can: unique email, atomic single-document writes, a TTL index that auto-purges old notifications.

18 collections, centred on the User entity.

Security-shaped

04 · Database · Integrity

Indexing & atomic integrity

Indexing strategy

  • A B-tree index turns find() from an O(n) scan into an O(log n) lookup.
  • Compound indexes like { user, createdAt:-1 } filter and return pre-sorted — no in-memory sort.
  • Indexes added on 8 collections covering the hot queries: logins, sessions, notifications, resources, games, leaderboard.
  • A TTL index auto-deletes notifications after 90 days — no cron job.

No double-booking

Availability.findOneAndUpdate( { mentor, 'slots.i.isBooked': false }, // only if free { $set: { 'slots.i.isBooked': true } }, // claim it { new: true } )

Filter + write happen as one atomic operation. If two mentees race, exactly one matches and wins; the other is told “already booked.”

05 · System Architecture

How the pieces fit together

Browser (React SPA) ──HTTPS REST──▶ Express ─▶ Mongoose ─▶ MongoDB │ ──WebSocket───▶ Socket.IO (realtime rooms · signaling) │ └────────── peer-to-peer video (WebRTC) ──────────┘

Layered server

middleware → routing → auth/validate → handler → model → central error handler.

Stateless JWT auth

No server session store — the same code can run as multiple processes and scale horizontally.

Isolated subsystems

AI (Groq/Gemini), code execution (Judge0 sandbox) and video (WebRTC) are independent — one failing never takes the platform down.

05 · Architecture · Request Lifecycle

Booking a slot, end to end

  1. axios attaches the JWT → PATCH /api/availability/book/<slot>
  2. CORS → body parse → request-id assigned → rate limit checked
  3. protect verifies the JWT signature and token freshness
  4. Handler runs the atomic conditional update against the slot
  5. MongoDB executes it atomically → returns the booked slot, or null
  6. Response: 200 booked  ·  409 already taken
  7. Any thrown error → the central handler maps it to the right status & logs it with the request-id
06 · Implementation Approach

Harden in place — don't rewrite

The app is feature-complete but not yet safe. A rewrite would throw away working code and risk the student handoff. So the plan is to make the existing platform production-grade in small, verifiable steps.

Methodology

Security-first — fix exploitable issues before polish.

Small increments — each change is backward-compatible and reuses shared helpers.

Evidence before “done” — nothing is claimed complete without an observed test pass.
